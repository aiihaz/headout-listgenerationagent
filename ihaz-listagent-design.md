## Problem Statement

Headout signs 50+ new supplier experiences per month. Each listing currently takes
2-4 hours of manual catalog associate work: read supplier data (PDFs, emails, CSVs),
research the experience, write all copy, structure variants, add SEO tags, publish.
Quality varies by who writes it. No AI assistance, no structured extraction, no quality
gate beyond human judgment.

At 50+ experiences/month and 2-4 hours each, this is 100-200 hours/month of
bottlenecked catalog work. The goal is an AI pipeline that removes the content
production step from the associate's workflow entirely — leaving only review and approval.

## Demand Evidence

Headout commissioned this as an evaluation assignment, indicating direct organizational
intent to solve the problem. The stated figures (2-4 hrs/listing, 50+ experiences/month,
quality variance) are the brief's own characterization of the pain. Primary user demand
was inferred from the problem statement rather than observed directly — this is a known
gap that should be validated with a catalog associate before the tool ships.

## Status Quo

Catalog associate receives raw supplier data in any format. Manually extracts
information. Writes all copy from scratch. Structures variants. Adds SEO metadata.
Publishes. No template, no AI assist, no structured handoff from supplier. The
workaround is the person.

## Target User and Narrowest Wedge

**Primary user:** Catalog associate — the person whose 2-4 hours this replaces.
**Secondary user:** The VP/product team evaluating whether to build this.

**Narrowest wedge that gets greenlit:** A demo where real supplier data (including
the three ambiguous cases from the brief) goes in and a structured listing JSON comes
out — with explicit null fields where information is absent rather than fabricated
values. The listing looks publishable. The architecture shows how it scales.

## Constraints

- Assignment scope: CLI/script, not CMS-integrated
- Output: JSON matching assignment spec (Title, Description, Variants, FAQs, SEO tags,
  Publish Readiness Verdict with field-level reasons)
- Must handle the three explicit ambiguity cases from the brief without fabrication
- Must demonstrate architectural clarity alongside output quality

## Premises

1. **Ambiguity classification is the hardest part, not copy generation.** Getting the
   writing right is table stakes. The differentiation is in how unknown/conditional/
   contradicted fields are handled. An evaluator who's seen 100 demos will notice
   the ambiguity framework immediately.

2. **The Intake Agent must return null for unknown fields.** A partial intake.json with
   honest nulls is more valuable than a complete one with guessed values. "Policy-induced
   hallucination" — models fabricating plausible values when configured to always produce
   complete output — is the dominant failure mode in production listing pipelines (per
   2025-26 landscape research). The fix: explicitly permit uncertainty in every extraction
   prompt.

3. **Review Agent checks three layers, not one.** Factual accuracy vs intake.json (did
   the copy invent anything?), Headout voice compliance (does it follow the brand rules?),
   SEO completeness (title length, meta description, tags present?). These three layers
   operationalize "quality" without requiring subjective taste calls. The Review Agent
   has no creative judgment — only rule-checking.

4. **Publish verdict is binary with field-level reasons.** The associate needs a clear
   action: publish or fix. "Conditional pass with warnings" is a UX failure — it
   becomes a list nobody reads. But "Needs Human Review — tower access claim not
   traceable to intake data" is actionable.

5. **Output is structured JSON to the assignment spec.** Not a CMS push. The evaluation
   is of the pipeline's logic, not its integrations.

6. **Ambiguity detection is two-pass.** The Intake Agent pre-screens the raw input for
   obvious vagueness, and also flags ambiguities discovered during field-level extraction.
   Latent ambiguity — where text looks clear until you try to extract a structured value
   and realize two interpretations are equally plausible — is more dangerous than obvious
   vagueness. Both passes are required.

## The Ambiguity Framework

This is the design's core intellectual contribution. Every field in intake.json carries
a confidence state:

| State | Meaning | Example |
|---|---|---|
| `EXPLICIT` | Supplier stated it clearly | "Valid 365 days, no blackout dates" |
| `INFERRED` | Supplier implied it, not stated | "Open daily" → probably no blackout dates |
| `CONDITIONAL` | Supplier gave a hedge | "Contact us for special closures" |
| `SILENT` | Supplier never mentioned it | No mention of blackout dates at all |
| `CONTRADICTED` | Two sources say different things | PDF says 9am start; email says 10am |

These states drive different output behaviors:

- `EXPLICIT` → state confidently in listing copy
- `INFERRED` → state with soft language ("typically," "generally")
- `CONDITIONAL` → surface the condition honestly in the listing
- `SILENT` → omit the field or say "check with operator before visiting"
- `CONTRADICTED` → force "Needs Human Review" regardless of other fields

**Handling the three brief-specific cases:**

| Input | Classification | Output |
|---|---|---|
| "no blackout dates listed" | `SILENT` (supplier said nothing) | Omit or: "check availability before booking" |
| "Contact us for special closures" | `CONDITIONAL` | "Subject to special closures — contact operator for details" |
| Tower access "not guaranteed" | `CONDITIONAL` on a key selling point | Exclude from title/highlights; include in Exclusions with exact language |

Note: "no blackout dates listed" is NOT the same as "no blackout dates." The first is
silence; the second is an explicit claim. The Intake Agent must distinguish these.

Chain-of-thought on throughout.

## Approaches Considered

### Approach A: Linear Three-Prompt Pipeline
Three sequential LLM calls: Intake → Content → Review. Pydantic schemas enforce
null+null_reason. No orchestration overhead.
- Effort: S | Risk: Low
- Pro: Ships immediately, easy to demo, full prompt control
- Con: Full re-run on any failure, no parallelism, weaker architecture story

### Approach B: Multi-Agent with Targeted Regeneration (CHOSEN)
Orchestrator manages state across four components. Intake Agent does two-pass
ambiguity classification. Content Generator and Template Engine run in parallel.
Review Agent checks 3 layers; only failing fields regenerate.
- Effort: M | Risk: Medium
- Pro: Architecture IS the demo; targeted regen saves cost and quality; deterministic
  Template Engine eliminates hallucination on structured data fields
- Con: More moving parts, longer to get running

### Approach C: Deterministic-First Hybrid
Deterministic parsers handle structured fields (pricing, times, locations) first;
LLM only handles free-text. Small classifier pre-screens for ambiguity.
- Effort: M-L | Risk: Medium-High
- Pro: Near-zero hallucination on structured fields
- Con: Brittle to format variations, overengineered for assignment scope

## Recommended Approach: B — Multi-Agent with Targeted Regeneration

### Intake Agent: Two-Pass Implementation

Both passes run inside a single LLM call using chain-of-thought structure:

```
SYSTEM: You are a structured data extractor. Never infer. Never fill nulls.
        If a field is not present in the source, return null with a reason.

PROMPT:
Step 1 (pre-screen): Read the raw supplier input. List every phrase that is
  vague, hedged, contradictory, or absent. Output as ambiguity_candidates[].

Step 2 (field extraction): For each required listing field, extract the value.
  For each field, output:
    - value: the extracted value, or null
    - confidence_state: EXPLICIT | INFERRED | CONDITIONAL | SILENT | CONTRADICTED
    - source_quote: the exact phrase from the input, or null
    - null_reason: why the field is null (if applicable)
  Cross-reference ambiguity_candidates[] during extraction. If a candidate
  applies to this field, set confidence_state accordingly.

Output: valid intake.json matching the schema below.
```

This design means latent ambiguity (text that looks clear but has multiple
valid interpretations) is caught during Step 2 when field extraction forces
a resolution — not pre-screened away in Step 1.

### Template Engine Field Mapping

The Template Engine is deterministic Python code — no LLM. It maps intake.json
fields to structured listing output using simple conditionals.

| intake.json field | listing.json field | Rule |
|---|---|---|
| `title` (EXPLICIT/INFERRED) | `listing.title` | Direct map |
| `duration` | `listing.structured_data.duration` | ISO 8601 format |
| `price_tiers[*]` | `listing.variants[*]` | One variant per tier |
| `price_tiers[*].adult_price` | `listing.variants[*].price` | Number |
| `inclusions[]` (EXPLICIT only) | `listing.inclusions[]` | Omit INFERRED/SILENT |
| `exclusions[]` | `listing.exclusions[]` | Include CONDITIONAL with hedge |
| `operating_days` | `listing.structured_data.openingHours` | Schema.org format |
| `faqs[]` (from intake) | `listing.structured_data.faqPage` | FAQPage JSON-LD |
| Any field with `SILENT` state | (omitted) | Never placeholder |
| Any field with `CONTRADICTED` | Pipeline halt | Returns error before Template Engine runs |

Variant schema (single-axis, for demo):
```json
{
  "variants": [
    {"name": "Adult", "price": 29.99, "currency": "USD", "description": null},
    {"name": "Child (3-12)", "price": 19.99, "currency": "USD", "description": null}
  ]
}
```

### Targeted Regeneration: Exact Inputs

When the Review Agent returns FAIL, the Content Generator reruns with these
exact inputs (and nothing else):

```python
regen_input = {
    "intake_json": intake_json,           # Full intake.json, unchanged
    "passing_fields": {                    # Immutable — not regenerated
        k: v for k, v in listing_draft.items()
        if k not in [b["field"] for b in review.blockers]
    },
    "failing_fields": {                    # These will be regenerated
        b["field"]: {
            "previous_value": listing_draft[b["field"]],
            "fix_instruction": b["fix_instruction"],
            "layer": b["layer"]
        }
        for b in review.blockers
    },
    "temperature": 0.3                     # Reduced from 0.7 — less variance
}
```

The Content Generator must not modify any passing field. The fix instruction
per blocker is the only directive — not the full content generation prompt.

### Review Agent: All 25 Checks Defined

**Layer 1 — Factual Accuracy (9 checks)**
1. Every claim in the title traces to intake.json with EXPLICIT or INFERRED confidence
2. Every claim in the description traces to intake.json (no invented details)
3. No CONDITIONAL qualifier was omitted or softened in copy (e.g., "tower access not guaranteed" cannot become "includes tower access")
4. SILENT fields are either omitted or use hedged language — never stated as fact
5. INFERRED fields use soft language ("typically," "generally") not declarative language
6. Each inclusion bullet point traces to an EXPLICIT or INFERRED intake field
7. Each exclusion bullet point traces to an intake field or a CONDITIONAL hedge
8. Variant prices match intake.json pricing fields exactly
9. Operating hours/days match intake.json with the correct confidence state applied in copy

**Layer 2 — Voice Compliance (8 checks)**
1. Title leads with the experience category or location, not a brand name
2. Description opens with an outcome/benefit sentence, not logistics
3. Highlights are specific claims, not adjectives ("skip-the-line access" not "convenient")
4. No first-person language ("we offer," "our guides," "you'll love")
5. Sentences are active voice — no passive constructions
6. No pricing references in description copy
7. Each FAQ answers the specific question asked — not a restatement of the listing
8. No fabricated superlatives without a traceable source claim in intake.json

**Layer 3 — SEO Completeness (8 checks)**
1. Title is 50-65 characters
2. Meta description is 140-160 characters
3. At least 5 SEO tags present
4. Tags include location, experience type, and at least one key inclusion
5. Title includes the primary experience keyword
6. Meta description includes a benefit or call-to-action phrase
7. Structured data block has `name`, `description`, and `url` fields populated
8. Structured data `duration` field is present if duration exists in intake.json

### Error Handling

| Failure | Behavior |
|---|---|
| LLM API timeout (>30s) | Retry once with exponential backoff. After 2nd timeout, halt and return `{error: "LLM_TIMEOUT", stage: "<agent_name>"}`. |
| LLM returns malformed JSON | Retry once with explicit format reminder in prompt. After 2nd malformed response, halt with `{error: "INVALID_JSON", stage: "<agent_name>", raw_response: "..."}`. |
| CONTRADICTED field in intake | Halt immediately before content generation. Return `{verdict: "NEEDS_HUMAN_REVIEW", reason: "CONTRADICTED_FIELD", field: "...", values: [...]}`. |
| Review Agent returns FAIL twice | Halt. Return `{verdict: "NEEDS_HUMAN_REVIEW", reason: "REGEN_FAILED", failing_fields: [...], last_review: review.json}`. |
| Template Engine omits required field | Log to metadata sidecar. Do not fail the pipeline — omissions are intentional. |

### Demo Run Plan

Two runs demonstrate the full system:

**Run 1 (happy path):** Clean supplier input with CONDITIONAL fields (special closures,
tower access) but no CONTRADICTIONS. Shows: two-pass ambiguity classification, honest
null fields, published listing with correctly hedged language. Demonstrates PASS path.

**Run 2 (escalation path):** Same supplier but with a deliberate CONTRADICTION injected
(e.g., PDF says "9:00 AM daily," email says "10:00 AM start"). Shows: early halt before
content generation, field-level reason in the verdict output. Demonstrates that the
system refuses to guess when sources conflict.

This guarantees both the listing quality story (Run 1) and the trust story (Run 2)
are visible without relying on the Review Agent catching a fabrication by chance.

### Parallelism Note

In the demo implementation, Content Generator and Template Engine run sequentially
for simplicity. The architecture supports parallelism via `asyncio.gather()` — both
take `intake.json` as input and have no shared state. To parallelize:

```python
listing_draft, template_output = await asyncio.gather(
    content_generator.run(intake),
    template_engine.run(intake)
)
```

The sequential demo produces identical output; parallelism is an optimization for
production throughput, not a correctness requirement.

### Key Design Decisions

**1. The Template Engine never invents.** If a field is null or SILENT in intake,
it is omitted from structured output — not replaced with a placeholder. A metadata
sidecar logs every intentional omission. The Review Agent knows what was deliberately
excluded vs what was missed.

**2. Chain-of-thought throughout.** Research shows CoT cuts hallucination roughly
50% (38% → 18%). All three LLM agents use CoT in their extraction and generation
prompts.

**3. The Review Agent never sees the Content Generator's instructions.** It evaluates
against two fixed references only: intake.json (facts) and a hardcoded voice ruleset
(quality). This eliminates the self-grading problem — a model cannot be a reliable
judge of its own output.

**4. CONTRADICTED fields block immediately.** When two sources say different things
(e.g., PDF says 9am, email says 10am), the pipeline halts and returns Needs Human
Review before content generation even starts. There is no "average the two values."

**5. Targeted regeneration, not full reruns.** When the Review Agent returns FAIL,
only the specific failing fields regenerate with the fix instruction as context.
Temperature drops from 0.7 to 0.3 for regeneration — reduce variance, not increase it.

## Open Questions

1. **Headout voice guidelines.** The Review Agent's Layer 2 check requires a defined
   voice ruleset. This doesn't exist in the assignment brief. It must be written before
   the Review Agent prompt is designed. See Assignment below.

2. **Model selection.** The architecture is model-agnostic. Claude Sonnet 4.6 for all
   three agents is a reasonable default (strong instruction following, good at structured
   output). GPT-4o is a valid alternative. Budget and latency targets should drive this.

3. **Variant complexity.** Real Headout listings have multi-dimensional variants
   (Private vs Group, With Transfers vs Without). The assignment asks for variants
   with pricing logic but doesn't specify the max complexity. For the demo, assume
   single-axis variants (e.g., Adult/Child pricing or Standard/Premium tiers).

4. **Supplier data format.** We have three example ambiguity cases from the brief
   but not a real supplier dataset. The demo needs a realistic fake — a plausible
   supplier info pack for a city tour or attraction ticket.
